무엇해결하는 것이 수업에서의 쓸모
① 깃내 컴퓨터 안의 기록과 되돌리기 AI 가 고친 것을 되돌린다
② 깃허브남과 나누기와 백업 분석을 제출하고 재현시킨다
③ 클로드 + 깃커밋·PR 을 맡기기 기록을 남기는 품을 줄인다

일단 이 넷이면 된다

터미널
git init      이 폴더를 기록 대상으로
git status    지금 뭐가 바뀌었나
git add .     기록할 것을 고른다
git commit    이름 붙여 남긴다
  -m "동별 요약 로직 확정"

git log --oneline   지금까지의 기록
git diff            무엇이 바뀌었나

되돌리는 명령은 위험해서 여기 적지 않았다. 필요할 때 클로드에게 물어본다 — 무엇이 지워지는지 설명을 듣고 승인한다.

"무엇을 왜 바꿨는지" 를 적는다. 석 달 뒤에 이 목록만 읽고도 분석의 흐름이 보여야 한다.

① 깃

넣지 않을 것 — .gitignore

넣지 않는다왜
인증키 · 비밀번호 한 번 올라가면 지워도 기록에 남는다. 저장소를 공개로 바꾸는 순간 노출된다
큰 원본 데이터수백 MB 를 커밋하면 저장소가 감당하지 못한다. 받는 방법을 적어 두면 된다
개인정보가 든 자료3주차에 말한 비공개 데이터가 여기 해당한다
다시 만들 수 있는 것그림·PDF 처럼 스크립트로 재생성되는 산출물
.gitignore
.env            # 인증키
data/raw/       # 원본 데이터 — README 에 받는 법을 적는다
output/*.png    # 스크립트로 다시 만든다

첫 커밋 전에 .gitignore 부터 만든다. 올라간 뒤에 지우는 것은 훨씬 어렵다.

② 깃허브

내 컴퓨터 밖에 두기

깃은 내 컴퓨터 안의 기록이다. 노트북이 고장 나면 함께 사라진다.

깃허브는 그 기록을 인터넷에 올려 두는 곳이다. 백업이자, 남에게 보여 주는 창구다.

터미널 · gh 를 설치하고 로그인한 뒤
gh auth login          한 번만
gh repo create         저장소 만들기
git push               올리기
git pull               내려받기

공개할 것과 하지 않을 것

이 수업이라면
공개(public) 분석 스크립트 · 로직 문서 · 결과표 · README
비공개(private) 확정 전 초안, 개인정보가 섞였을 가능성이 있는 것

공개는 되돌리기 어렵다. 헷갈리면 비공개로 만들고 나중에 바꾼다 — 반대 방향은 이미 늦다.

COMPAS 비공개 데이터는 어느 쪽에도 올리지 않는다.

② 깃허브

README — 재현의 설명서

남이 이 저장소를 열었을 때 가장 먼저 보는 화면이다.

이 수업의 기준은 하나다 — 이것만 읽고 내 결과를 다시 만들 수 있는가.

원본 데이터를 올리지 않는 대신 받는 방법을 적는다. 그것이 3주차 "데이터 출처 문서" 가 여기로 오는 자리다.

README.md
# 청주 상당구 실거래가 분석

## 무엇을 했나
동별 ㎡당 가격을 비교했다.

## 데이터
국토부 실거래가 API (공공데이터포털)
상당구 43111 · 2025.10~2026.09
받는 법: 인증키를 발급받아
`.env` 에 넣고 `python fetch.py`

## 분석 규칙
CLAUDE.md 참조 (60㎡ 초과 · 중앙값)

## 다시 만들려면
`python fetch.py` → `python summary.py`
결과는 `output/` 에

③ 클로드 + 깃

기록하는 품을 맡긴다

클로드 코드는 터미널에서 돌므로 깃 명령을 그대로 쓸 수 있다

이렇게 시킨다

"지금까지 바뀐 걸 무엇을 왜 바꿨는지 알 수 있게 커밋해 줘. 커밋하기 전에 무엇을 담을지 목록으로 보여 줘."

".env 는 빼고 커밋해."

"이 저장소의 커밋 기록을 읽고 분석이 어떻게 바뀌어 왔는지 정리해 줘."

굵게 표시한 부분이 핵심이다. 커밋 전에 목록을 보여 달라고 한다 — 무엇이 올라가는지 모르고 승인하면 인증키가 함께 간다.

마지막 줄은 이 수업다운 쓰임이다 — 커밋 기록 자체가 분석 과정의 증거가 된다.

PR — 합치기 전에 보여 주기

풀 리퀘스트(PR)는 "이렇게 바꾸려는데 봐 주세요" 라는 요청이다. 바뀐 부분이 한눈에 보이고, 줄마다 의견을 달 수 있다.

터미널
git switch -c 면적하한-실험
# … 작업 …
git push -u origin 면적하한-실험
gh pr create

클로드에게 "브랜치 만들고 PR 까지 올려 줘" 라고 해도 된다. 올리기 전에 무엇을 담을지 확인한다.

GitHub Actions 위에서 돌기 때문에 저장소 관리자 권한과 인증 설정이 필요하다. 팀으로 일할 때 쓰는 기능이라 오늘은 개념만 본다.

주의 — 이 수업에서 실제로 겪는 사고

사고막는 법
인증키를 커밋했다 첫 커밋 전에 .gitignore 부터 만든다. 이미 올렸다면 그 키를 폐기하고 새로 발급받는다 — 기록에서 지우는 것보다 그게 빠르고 확실하다
비공개 데이터를 올렸다COMPAS 비공개분·개인정보는 저장소에 넣지 않는다. 받는 방법만 적는다
큰 파일로 저장소가 막혔다원본 데이터는 .gitignore 로 뺀다
AI 가 고친 걸 못 되돌린다작업을 시작하기 전에 커밋해 둔다. 되돌릴 지점이 있어야 마음 놓고 시킨다

첫 줄이 가장 흔하고 가장 아프다. 공개 저장소는 검색된다.

실습

내 분석을 저장소로 만들기 — 약 1시간 30분

오늘 실습의 도착점

남이 README 만 보고 내 결과를 다시 만들 수 있는 저장소

시각할 일끝났다는 신호
0:00–0:25① 기록을 시작한다첫 커밋이 남았다
0:25–0:55② 브랜치로 실험하고 되돌린다main 이 그대로다
0:55–1:30③ 서로 재현해 본다남의 결과를 내가 만들었다

시작 전 확인

  • 지난주 ds2026/ 폴더 (CLAUDE.md · 스킬 · 에이전트가 들어 있다)
  • 깃 설치 · 깃허브 계정 · gh 설치

③은 짝이 필요하다. 홀수면 셋이 한 조로 돌려 가며 한다.

① 기록을 시작한다 0:00–0:25

  1. gh auth login 으로 로그인한다 (브라우저가 열린다) 5분
  2. ds2026/ 에서 git init 1분
  3. 커밋하기 전에 .gitignore 를 만든다 8분
  4. git status 로 올라갈 목록을 눈으로 읽는다 3분
  5. git add . → git commit -m "…" 3분

3번을 이렇게 시킨다

"이 폴더를 깃 저장소로 만들려고 해. 먼저 어떤 파일이 올라가면 안 되는지 목록으로 알려 주고 .gitignore 초안을 보여 줘. 내가 확인하면 커밋하자."

✓ 확인 지점 — git status 목록에 인증키·원본 CSV 가 없다. 보이면 .gitignore 를 고치고 다시 본다.

② 실험하고 되돌린다 0:25–0:55

  1. git switch -c 면적하한-실험 2분
  2. CLAUDE.md 의 면적 하한을 85㎡ 로 바꾸고 분석을 다시 돌린다 10분
  3. git diff 로 무엇이 바뀌었는지 보고 커밋한다 5분
  4. git switch main 으로 돌아간다 2분
  5. CLAUDE.md 를 열어 본다. 분석도 다시 돌려 본다 6분
  6. 실험을 살릴지 버릴지 정하고, 버릴 거면 브랜치를 지운다 5분
✓ 확인 지점 — 5번에서 CLAUDE.md 가 60㎡ 로 돌아와 있다. 결과표도 원래 값이다. 실험이 본 작업을 건드리지 않았다.
switch 가 거부되면 — 저장하지 않은 변경이 있는 것이다. 커밋하거나 되돌린 뒤 다시 한다. 무엇을 어떻게 할지는 클로드에게 물어보고 설명을 듣고 승인한다.

③-1 올리고 설명서를 쓴다 0:55–1:15

  1. gh repo create 로 저장소를 만들고 올린다. 공개 여부를 스스로 정하고 이유를 한 줄 적는다 7분
  2. README.md 를 쓴다 10분
  3. 커밋하고 올린다. 브라우저로 저장소를 열어 눈으로 확인한다 3분

README 에 반드시 들어갈 넷

무엇을 했나한두 문장
데이터 받는 법출처 · 조건 · 인증키를 어디에 넣나 (3주차 출처 문서를 옮긴다)
분석 규칙CLAUDE.md 를 가리키고 요점만
다시 만드는 순서실행할 명령을 순서대로
✓ 확인 지점 — 브라우저에서 저장소를 열었을 때 인증키도 원본 데이터도 보이지 않는다.

③-2 서로 재현해 본다 1:15–1:30

  1. 옆 사람과 저장소 주소를 바꾼다 1분
  2. 상대 저장소를 받는다 — git clone <주소> 2분
  3. README 만 보고 상대의 결과를 다시 만들어 본다. 막히면 물어보지 말고 그 지점을 적는다 8분
  4. 막힌 지점을 상대에게 알려 준다. 받은 지적으로 자기 README 를 고친다 4분
✓ 확인 지점 — 상대의 결과표와 같은 숫자가 나온다. 안 나오면 README 에 빠진 것이 있다는 뜻이고, 그 발견이 오늘의 성과다.
시간이 모자라면 — 3번의 막힌 지점 목록까지만 하고 4번은 집에서. 일찍 끝났으면 상대 저장소에 브랜치를 만들어 README 를 고치고 PR 을 올려 본다.

제출물

무엇어느 정도면 되나
저장소 주소공개 여부와 그렇게 정한 이유 한 줄
커밋 기록git log --oneline 결과. 메시지만 읽고 흐름이 보여야 한다
README넷이 다 있고 ③-2 로 고친 흔적이 있을 것
재현 후기상대 저장소에서 어디서 막혔는지와 내 README 를 어떻게 고쳤는지

마지막 줄이 이 강의의 핵심이다. 내가 아는 것과 적어 둔 것은 다르다 — 남이 막히는 자리에서만 그 차이가 드러난다.

다음 주부터 매주 실습 결과를 이 저장소에 커밋한다. 14주차에는 이 기록 전체가 증거 패키지의 바탕이 된다.
